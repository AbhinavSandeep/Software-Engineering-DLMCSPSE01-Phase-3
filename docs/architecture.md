# XPtoIRL architecture documentation

Version 1.0.0 (finalization phase). The structure follows the main views of arc42.

## 1. Context

Visitors, registered users and administrators use the web application through HTTPS. The application and a
PostgreSQL database run on a cloud platform (Render). GitHub hosts the code and runs CI. External game pages and
study DOIs are only linked, never loaded.

## 2. Building blocks (layered architecture)

| Layer | Building blocks | Code |
|-------|-----------------|------|
| Presentation | Jinja2 templates, CSS, JavaScript | `app/templates`, `app/static` |
| Controllers | Blueprints `catalogue`, `recommend`, `games`, `auth`, `account`, `admin`, `api` | `app/controllers` |
| Services | `recommendation`, `filters`, `catalogue`, `users`, `importer` | `app/services` |
| Data access | SQLAlchemy models `Skill`, `Game`, `Source`, `SkillGameMapping`, `User`, `Favourite`, `Rating` | `app/models.py` |
| Infrastructure | PostgreSQL / SQLite, Alembic migrations, configuration, Docker | `migrations`, `app/config.py`, `Dockerfile` |

Rule: a layer only uses the layer below. Services never import Flask request objects, which keeps them unit-testable.

## 3. Recommendation score

```
score(g) = Σ over selected skills s:  strength(g, s) × weight(evidence(g, s))
           + 0.5 × (avg_rating(g) − 3) / 2      if the game has ≥ 3 ratings for the selected skills
weight: A = 1.0, B = 0.7, C = 0.4      evidence(g, s) = best level among the mapping's sources
ties: more sources first, then title
```

## 4. Runtime view: "Find games"

1. The browser sends `GET /recommend?skill=teamwork&skill=communication&price_model=free`.
2. The `recommend` controller calls `recommendation.resolve_skills()` (checks 1 to 3 skills) and
   `GameFilter.from_args()` (ignores invalid values).
3. `recommendation.recommend()` loads the mappings of the selected skills with the filter applied, loads the rating
   averages in one grouped query and computes the score per game.
4. The controller renders `results.html` with the ranked results and the saved state of the user's learning plan.

## 5. Deployment view

`docker compose up` starts two containers: `web` (Python 3.12, Gunicorn, port 8000, host port changeable with `WEB_PORT`) and `db` (PostgreSQL 16 with a
named volume). In the cloud the same image runs as a Render web service with a managed PostgreSQL database; `render.yaml` describes
both as a Blueprint, and Gunicorn listens on the port that Render passes in `PORT`.

## 6. Design decisions

| ID | Decision | Rationale | Alternatives |
|----|----------|-----------|--------------|
| D1 | Server-side rendering with Flask and Jinja2 | One code base, works without JavaScript, simple for one developer | React SPA + API (more code, two deployments) |
| D2 | Rule-based, explainable score | Transparency (O3) and trust; testable with fixed numbers | Collaborative filtering (needs many users, not explainable) |
| D3 | Mapping as association class with ≥ 1 source | Enforces NFR9; keeps strength and reason per link | Plain many-to-many table (no place for reason and sources) |
| D4 | CSV files as the master data set, imported idempotently | Versioned in Git, easy to review; restore after database loss (R4) | Manual entry only (no history, slow) |
| D5 | All-or-nothing import with collected error list | No half-imported data; all problems fixed in one pass | Row-by-row import (inconsistent state) |
| D6 | SQLite locally and in tests, PostgreSQL in Docker and cloud | Fast tests without services; same SQLAlchemy code | PostgreSQL everywhere (slower setup) |
| D7 | Flask-Login, Flask-WTF CSRF, Werkzeug hashing | Proven security code (R5) instead of own implementation | Own session and token code |
| D8 | Read-only JSON API exempt from CSRF | GET only, no state change; allows health checks | Full REST API (not needed for release 1.0) |
| D9 | Infrastructure as code with `render.yaml` | Repeatable cloud set-up, no manual clicks; secrets generated by Render | Manual dashboard set-up (error-prone) |
| D10 | Direct dependencies pinned, including WTForms | Same versions locally, in CI and in Docker; avoids surprise deprecations | Unpinned versions |

## 7. Quality measures

- 86 automated tests (pytest), 93 % statement coverage of the service layer (target ≥ 70 %).
- Ruff lint in CI; a failing test or lint error blocks the merge.
- Database check constraints for PEGI, price model, play mode, strength, rating score and roles.
- Load test (NFR2), 27 Oct 2026, `scripts/load_test.py` against `docker compose` with PostgreSQL: 20 parallel users,
  500 page requests, 0 errors, median 267 ms, 95th percentile 385 ms (target < 1.5 s).
- Accessibility (NFR7): axe-core 4.10 with the WCAG 2.1 A/AA rules on the start, results, game, search, how-it-works and
  register pages: 0 violations.
- Fresh start (NFR3, O6): `docker compose up --build` on the developer PC migrates the PostgreSQL database, imports the
  data set and serves the application; a restart skips the import.
- Security: hashed passwords, CSRF tokens on all forms, role check for the admin area, open-redirect protection,
  secure cookies in production, the same error message for wrong e-mail and wrong password.

## 8. Technical debt (release 1.0)

Resolved in the finalization phase: Docker Compose start on the developer PC, load test, automated accessibility check,
WTForms deprecation warnings, cloud set-up as a Blueprint.

| Item | Impact | Possible solution |
|------|--------|-------------------|
| No moderated usability test with 3 to 5 external users (NFR1) | Ease of use only checked by the developer walkthrough (≤ 3 clicks to a result) | Run a think-aloud test with 5 users of the target group |
| No password reset and no e-mail confirmation | A user who forgets the password needs a new account | Add a mail service and signed reset tokens |
| Game facts entered by hand | PEGI ratings, platforms or price models may become outdated | Check before each release or import from a games API |
| Free cloud plan | The service sleeps after inactivity, the first request can take about a minute; the free database expires after the free period | Paid plan for permanent operation |
| Bootstrap loaded from the jsDelivr CDN | Styling depends on an external server | Bundle the files in `app/static` |
| Uptime of ≥ 99 % (NFR5) not measured | Availability is not proven over a longer period | External uptime monitor on `/api/health` |
